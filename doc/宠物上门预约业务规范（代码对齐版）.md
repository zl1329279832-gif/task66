## 2. 码值定义

### 2.1 `chongwu_yuyue_yesno_types`（审核状态）

> 字典码 `dicCode = "chongwu_yuyue_yesno_types"`，运行时存储于 `dictionary` 表。

| 码值 | 含义 | 前端显示 | 说明 |
|------|------|----------|------|
| **1** | 待审核 | （默认，创建时自动赋值） | 新预约提交后的初始状态 |
| **2** | 审核通过 | "同意" | 管理员审核通过，名额占用生效 |
| **3** | 审核拒绝 | "拒绝" | 管理员审核拒绝，名额不占用 |

**代码对应**：
- 创建时赋值：`ChongwuYuyueController /save` 与 `/add` 均 `setChongwuYuyueYesnoTypes(1)`
- 审核修改：`ChongwuYuyueServiceImpl.shenhe()` 根据管理员选择设为 `2` 或 `3`

### 2.2 `chongwu_yuyue_types`（预约进度）

> 常量定义于 `ChongwuYuyueEntity`（第 31-38 行）。

| 码值 | 常量名 | 含义 | 说明 |
|------|--------|------|------|
| **1** | `YUYUE_TYPE_PENDING` | 待审核 | 创建时默认值 |
| **2** | `YUYUE_TYPE_APPROVED` | 已通过 / 待进行 | 审核通过后自动设置 |
| **3** | `YUYUE_TYPE_IN_PROGRESS` | 进行中 | 通过 `/advance` 接口推进 |
| **4** | `YUYUE_TYPE_COMPLETED` | 已完成 | 通过 `/advance` 接口推进；触发评价资格 |

**两个字段的关系**：
- `yesno_types` 是**审核维度**（通过/拒绝），由 `/shenhe` 接口写入。
- `types` 是**业务进度维度**（服务履约流程），由 `/shenhe`（通过时联动写为2）和 `/advance`（2→3→4）写入。
- 拒绝（`yesno_types=3`）时 `types` 保持原值（仍为 1），仅靠 `yesno_types=3` 标识拒绝。

## 4. 核心业务流程详解

### 4.1 预约创建

**接口**：`POST /chongwuYuyue/save`（后台）、`POST /chongwuYuyue/add`（前端）

**处理逻辑**（`ChongwuYuyueController` 第 142-179 行、第 389-430 行）：

1. **用户身份绑定**：角色为"用户"时，从 Session 取 `userId` 强制写入 `yonghuId`，防止 IDOR 篡改。
2. **重复检查**：查询 `chongwu_id` + `yonghu_id` 组合下是否已存在 `yesnoTypes IN (1, 2)` 的记录。
   - 存在 `yesnoTypes=1` → 返回 "有相同的待审核的数据"
   - 存在 `yesnoTypes=2` → 返回 "有相同的审核通过的数据"
3. **时间冲突检查**：调用 `checkTimeConflict(chongwuId, yuyueTime, null)` 检测同一宠物同一时间是否已有有效预约。
4. **初始化状态**：`yesnoTypes=1`、`types=1`（`YUYUE_TYPE_PENDING`）。
5. **写入时间戳**：`insertTime` 和 `createTime` 均设为当前时间。

**结论：同一用户对同一宠物，在已有待审核或已通过记录时不能重复提交**。被拒绝（`yesnoTypes=3`）后可以重新提交。

### 4.2 审核（通过 / 拒绝）

**接口**：`POST /chongwuYuyue/shenhe`

**处理逻辑**（`ChongwuYuyueServiceImpl` 第 72-109 行）：

1. 根据 `id` 查询预约记录，不存在则返回错误。
2. **前置校验**：`yesnoTypes` 必须为 `1`（待审核）。已审核的记录不可重复操作。
3. **审核通过**（`yesnoResult=2`）：
   - 调用 `checkTimeConflict()` 检查时间冲突。冲突则拒绝通过并返回 "名额冲突，无法通过"。
   - 设置 `yesnoTypes=2`，`types=YUYUE_TYPE_APPROVED(2)`。
4. **审核拒绝**（`yesnoResult=3`）：
   - 设置 `yesnoTypes=3`。
   - `types` 字段**不修改**，保持为 `1`。
5. 保存审核回复文本（`yesnoText`，可选）和审核时间（`shenheTime`）。

**客服须知**：
- 审核通过后系统会改两个字段：`chongwu_yuyue_yesno_types` → 2，`chongwu_yuyue_types` → 2。
- 审核拒绝后系统只改一个字段：`chongwu_yuyue_yesno_types` → 3。
- 审核是不可逆操作，通过或拒绝后无法再次审核同一记录。

### 4.3 状态推进

**接口**：`POST /chongwuYuyue/advance/{id}`

**处理逻辑**（`ChongwuYuyueServiceImpl` 第 114-146 行）：

1. **权限校验**：普通用户只能推进自己的预约；管理员可操作任意预约。
2. **前置条件**：`yesnoTypes` 必须为 `2`（已通过审核）。
3. **状态推进**：
   - `types=2`（已通过）→ `types=3`（进行中）
   - `types=3`（进行中）→ `types=4`（已完成）
   - `types=4`（已完成）→ 返回 "无需再次推进"

### 4.4 列表查询与权限过滤

| 接口 | 用途 | 认证 | 用户过滤 |
|------|------|------|----------|
| `/page` | 后台管理列表 | 需要登录 | "用户"角色自动注入 `yonghuId`，只看自己的 |
| `/list` | 前端列表 | **`@IgnoreAuth` 免认证** | **无过滤，所有人可见全部预约** |
| `/info/{id}` | 后台详情 | 需要登录 | "用户"角色校验 `yonghuId` 一致 |
| `/detail/{id}` | 前端详情 | 需要登录 | "用户"角色校验 `yonghuId` 一致 |

## 5. 与 ChongwuLiuyan（评价/留言）的衔接

### 5.1 评价资格校验

评价（留言）由 `ChongwuLiuyanController` 的 `/save` 和 `/add` 接口处理。对"用户"角色增加了**预约完成前置校验**：

```
调用链路：
ChongwuLiuyanController /save 或 /add
  → chongwuYuyueService.hasCompletedBooking(userId, chongwuId)
    → 查询条件：yonghu_id = ? AND chongwu_id = ? AND yesno_types = 2 AND types = 4
    → 存在记录 → 允许评价
    → 不存在记录 → 返回 "您尚未完成该宠物的预约，无法评价"
```

**规则**（`ChongwuYuyueServiceImpl` 第 152-160 行）：
- 用户必须对该宠物有至少一条 `yesnoTypes=2`（审核通过）**且** `types=4`（已完成）的预约记录才能发表评价。
- 审核通过但未完成（`types=2` 或 `types=3`）的预约**不满足**评价条件。
- 被拒绝的预约（`yesnoTypes=3`）同样不满足。

### 5.2 关联方式

预约与评价之间**没有直接外键**关联。两张表通过 `chongwu_id`（宠物）+ `yonghu_id`（用户）的组合逻辑关联，由业务代码在评价提交时校验。

### 5.3 流程示意

```
用户预约宠物A → 管理员审核通过 → 推进到进行中 → 推进到已完成
                                                        |
                                                        v
                                            用户可以对宠物A发表评价
                                                        |
                                                        v
                                               管理员可在后台回复
                                             （ChongwuLiuyan.replyText）
```

## 6. 时段冲突检测

### 6.1 当前实现

时间冲突检测已实现，逻辑位于 `ChongwuYuyueServiceImpl.checkTimeConflict()`（第 47-64 行）。

**检测规则**：

```sql
SELECT * FROM chongwu_yuyue
WHERE chongwu_id = ?                              -- 同一宠物
  AND chongwu_yuyue_time = ?                       -- 精确时间戳匹配
  AND chongwu_yuyue_types IN (2, 3)                -- 已通过 或 进行中
  AND id != ?                                      -- 排除自身
```

**调用点**：

| 调用位置 | 时机 | 效果 |
|----------|------|------|
| `/save`（后台创建）第 162 行 | 用户提交新预约时 | 冲突则拒绝创建 |
| `/add`（前端创建）第 412 行 | 用户提交新预约时 | 冲突则拒绝创建 |
| `shenhe()`（审核通过）第 89 行 | 管理员通过审核时 | 冲突则拒绝通过 |

### 6.2 当前未实现：时间段范围冲突

> **重要提示**：当前冲突检测是**精确时间戳匹配**（`eq("chongwu_yuyue_time", yuyueTime)`），不是时间段/时间窗口的重叠检测。

这意味着：
- `2024-03-01 14:00:00` 和 `2024-03-01 14:00:00` 会被判定为冲突。
- `2024-03-01 14:00:00` 和 `2024-03-01 14:30:00` **不会**被判定为冲突，即使两个预约的服务时间可能重叠。

**影响**：如果上门服务需要持续一段时间（如 1 小时），当前检测无法防止时间段重叠的情况。需要评估是否要引入服务时长字段并改为范围重叠检测。

### 6.3 同一时段能否约两次？

回答取决于场景：

| 场景 | 能否同时存在？ | 原因 |
|------|---------------|------|
| 同一用户、同一宠物、完全相同时间 | 不能 | 重复检查（yesno IN 1,2）拦截 |
| 同一用户、同一宠物、不同时间 | 不能（有待审核/已通过的情况下） | 重复检查按 user+pet 组合拦截，不区分时间 |
| 不同用户、同一宠物、完全相同时间 | 不能 | 时间冲突检测拦截 |
| 不同用户、同一宠物、时间戳差异>0秒 | **可以** | 冲突检测只做精确匹配 |
| 同一用户、不同宠物、完全相同时间 | **可以** | 冲突检测仅按 chongwu_id 维度 |

## 7. 安全相关说明

### 7.1 IDOR 防护（用户只能看自己的单）

系统在多个接口对"用户"角色实施了 IDOR（越权访问）防护：

| 接口 | 防护方式 | 代码位置 |
|------|----------|----------|
| `/page` | 自动注入 `yonghuId` 到查询参数 | Controller 第 83-84 行 |
| `/info/{id}` | 查出记录后校验 `yonghuId` 是否匹配 Session | Controller 第 107-112 行 |
| `/detail/{id}` | 查出记录后校验 `yonghuId` 是否匹配 Session | Controller 第 353-358 行 |
| `/save` | 从 Session 强制覆盖 `yonghuId` | Controller 第 149-150 行 |
| `/add` | 从 Session 强制覆盖 `yonghuId` | Controller 第 395-397 行 |
| `/update` | 校验原记录 `yonghuId` 匹配 + 强制覆盖 | Controller 第 191-197 行 |
| `/advance/{id}` | 普通用户校验 `yonghuId` | Service 第 122-124 行 |

### 7.2 现存 IDOR 风险

**`/chongwuYuyue/list` 接口**（Controller 第 327-341 行）：

```java
@IgnoreAuth                    // ← 不需要登录
@RequestMapping("/list")
public R list(@RequestParam Map<String, Object> params, HttpServletRequest request){
    CommonUtil.checkMap(params);
    PageUtils page = chongwuYuyueService.queryPage(params);
    // ... 无 yonghuId 过滤
}
```

- 该接口标记了 `@IgnoreAuth`，**无需登录即可访问**。
- **不注入** `yonghuId` 过滤条件，任何人可查看全部用户的预约列表。
- 可能暴露用户的预约信息（预约时间、报名理由、审核状态等）。

**`/chongwuYuyue/shenhe` 接口**（Controller 第 208-212 行）：

- Controller 层**未校验操作者角色**，理论上任何已登录用户（包括普通"用户"角色）都可以调用审核接口。
- 前端通过 `isAuth('chongwuYuyue','审核')` 权限按钮控制可见性，但后端无对应拦截。

### 7.3 SQL 注入风险

`ChongwuYuyueDao.xml` 的 ORDER BY 子句使用了 `${}` 字符串拼接（第 169 行）：

```xml
order by a.${params.sort} ${params.order}
```

`${}` 不会进行参数化转义，如果 `sort` / `order` 参数来自用户输入且未在上游严格校验，存在 SQL 注入风险。`ChongwuLiuyanDao.xml` 同样存在此问题。
