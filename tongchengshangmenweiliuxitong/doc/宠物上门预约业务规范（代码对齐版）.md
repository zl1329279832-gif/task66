## 2. 码值字典速查

### 2.1 `chongwuYuyueYesnoTypes` — 审核状态（字典码 `chongwu_yuyue_yesno_types`）

| 码值 | 显示名 | 说明 | 谁写入 |
|:---:|---|---|---|
| **1** | 待审核 | 默认值，用户提交预约时自动设置 | `save()` / `add()` 自动赋值 |
| **2** | 同意 | 管理员审核通过，预约进入可推进状态 | `shenhe()` 审核通过时写入 |
| **3** | 拒绝 | 管理员审核拒绝，预约终止 | `shenhe()` 审核拒绝时写入 |

> 前端审核弹窗只提供 `同意(2)` 和 `拒绝(3)` 两个选项（Vue `list.vue` 第 987-1023 行）。
>
> **审核按钮仅当 `chongwuYuyueYesnoTypes == 1` 时可见**，已审核的记录不会再次显示审核入口。

### 2.2 `chongwuYuyueTypes` — 预约进度（Entity 静态常量）

| 码值 | 常量名 | 显示名 | 说明 |
|:---:|---|---|---|
| **1** | `YUYUE_TYPE_PENDING` | 待审核 | 预约刚创建，等待管理员审核 |
| **2** | `YUYUE_TYPE_APPROVED` | 已通过/待进行 | 审核通过，等待上门 |
| **3** | `YUYUE_TYPE_IN_PROGRESS` | 进行中 | 上门服务正在进行 |
| **4** | `YUYUE_TYPE_COMPLETED` | 已完成 | 服务完成，用户可发表评价 |

> 这两个字段的生命周期关系请见 §5 状态机图。

## 3. 预约创建流程

系统有 **两个创建入口**，字段校验逻辑基本一致：

### 3.1 后端管理入口 `POST /chongwuYuyue/save`

```
Controller.save()
  ├─ 1. 角色判断：若当前角色 = "用户"，yonghuId 强制取 session.userId
  ├─ 2. 重复校验（同宠物 + 同用户 + yesnoTypes ∈ {1,2}）
  │     └─ 若存在 → 返回错误（"有相同的待审核/审核通过的数据"）
  ├─ 3. 时间冲突检查：checkTimeConflict(chongwuId, yuyueTime, null)
  │     └─ 若冲突 → 返回 "该宠物在此时间段已有预约，请选择其他时间"
  ├─ 4. 设置初始值：
  │     ├─ chongwuYuyueYesnoTypes = 1  （待审核）
  │     ├─ chongwuYuyueTypes      = 1  （YUYUE_TYPE_PENDING）
  │     ├─ insertTime             = now
  │     └─ createTime             = now
  └─ 5. insert()
```

### 3.2 前端用户入口 `POST /chongwuYuyue/add`

```
Controller.add()
  ├─ 1. yonghuId 强制取 session.userId（防止 IDOR）
  ├─ 2. 重复校验（比 save 更严格，额外匹配 uuidNumber + text + yesnoText）
  │     └─ 注：有一行注释掉的 .notIn("chongwu_yuyue_types", new Integer[]{102})
  │        该 102 值在当前代码中无任何定义或引用，属于残留调试代码
  ├─ 3. 时间冲突检查（同 save）
  ├─ 4. 设置初始值（同 save）
  └─ 5. insert()
```

### 3.3 创建阶段字段变更汇总

| 字段 | 写入值 | 来源 |
|---|---|---|
| `chongwuYuyueYesnoTypes` | `1` | 代码硬编码 |
| `chongwuYuyueTypes` | `1`（YUYUE_TYPE_PENDING） | 静态常量 |
| `yonghuId` | session 中的用户 ID | 强制覆盖，不信任前端传值 |
| `insertTime` | `new Date()` | 服务器时间 |
| `createTime` | `new Date()` | 服务器时间 |
| 其余字段 | 前端表单提交 | 包括 `chongwuId`、`chongwuYuyueText`、`chongwuYuyueTime`、`chongwuYuyueUuidNumber` |

### 3.4 同一时段能否约两次？

**不能**，但判定粒度需注意：

- 冲突检测是 **精确到秒的等值匹配**（`eq("chongwu_yuyue_time", yuyueTime)`），不是时间范围重叠判断。
- 同一宠物在 `2026-06-15 10:00:00` 已有一条有效预约时，再次预约同一精确时刻会被拒绝。
- 但 `10:00:00` 和 `10:00:01` 被视为**不同时段**，不会被拦截（详见 §8）。

## 4. 审核流程（/shenhe）

### 4.1 接口定义

```
POST /chongwuYuyue/shenhe
Body: {
  "id": <预约ID>,
  "chongwuYuyueYesnoTypes": 2 或 3,    // 审核结论
  "chongwuYuyueYesnoText": "审核回复"    // 可选
}
```

> **Controller 层极简委托**：`shenhe()` 方法体只有一行 `return chongwuYuyueService.shenhe(entity)`，所有逻辑在 ServiceImpl 中。

### 4.2 审核通过（yesnoTypes = 2）字段变更

| 字段 | 变更前 | 变更后 | 说明 |
|---|---|---|---|
| `chongwuYuyueYesnoTypes` | `1` | **`2`** | 审核结论 → 同意 |
| `chongwuYuyueTypes` | `1`（待审核） | **`2`**（YUYUE_TYPE_APPROVED） | 进度推进到"已通过/待进行" |
| `chongwuYuyueYesnoText` | `null` 或旧值 | 管理员填写的回复 | 可为空 |
| `chongwuYuyueShenheTime` | `null` | **`new Date()`** | 记录审核时间 |

**审核通过前会执行时间冲突检查**：若该宠物在同一时刻已有 `types ∈ {2, 3}` 的预约 → 拒绝通过，返回"名额冲突"。

### 4.3 审核拒绝（yesnoTypes = 3）字段变更

| 字段 | 变更前 | 变更后 | 说明 |
|---|---|---|---|
| `chongwuYuyueYesnoTypes` | `1` | **`3`** | 审核结论 → 拒绝 |
| `chongwuYuyueTypes` | `1` | **`1`（不变）** | 进度不推进，保持待审核 |
| `chongwuYuyueYesnoText` | `null` 或旧值 | 管理员填写的回复 | 可为空 |
| `chongwuYuyueShenheTime` | `null` | **`new Date()`** | 记录审核时间 |

> **关键行为**：拒绝时 `chongwuYuyueTypes` 保持 `1`，不会设置为某个"已拒绝"状态值。代码注释原文：
> ```
> // types 保持原值或设为一个"已拒绝"标记；这里不复用进度枚举，仅靠 yesno=3 标识
> ```
> 这意味着被拒绝的预约在 `types` 维度上永远停在"待审核"，需通过 `yesnoTypes=3` 来区分"从未提交审核"和"被拒绝"。

### 4.4 审核前置校验

| 校验项 | 条件 | 失败提示 |
|---|---|---|
| 记录存在 | `selectById(id) != null` | "预约记录不存在" |
| 未重复审核 | `yesnoTypes == 1` | "该预约已审核，不可重复操作" |
| 审核值合法 | `yesnoResult == 2 \|\| 3` | "审核结果值非法，只能为2(通过)或3(拒绝)" |
| 时段不冲突 | 仅通过时检查 | "该宠物在此时间段已有预约，名额冲突，无法通过" |

### 4.5 注释掉的代码说明

`/add` 端点中有一行注释：
```java
//  .notIn("chongwu_yuyue_types", new Integer[]{102})
```
`102` 在当前代码和数据库字典中均无定义，推测为开发调试时临时排除某类测试数据的残留，**无业务含义**，可安全清理。

## 5. 预约状态机

### 5.1 完整状态机（ASCII）

```
                          ┌──────────────────────────────────┐
                          │          管理员审核               │
                          ▼                                  │
  ┌──────────┐   创建    ┌──────────┐   通过    ┌────────────┴───┐
  │  (不存在)  │────────▶│  待审核    │────────▶│ 已通过/待进行    │
  └──────────┘          │ yesno=1   │         │  yesno=2        │
                        │ types=1   │         │  types=2        │
                        └─────┬─────┘         └────────┬────────┘
                              │                        │
                         拒绝 │                   advance
                              │                        │
                              ▼                        ▼
                        ┌──────────┐          ┌────────────────┐
                        │  已拒绝   │          │    进行中        │
                        │ yesno=3  │          │   yesno=2       │
                        │ types=1  │          │   types=3       │
                        └──────────┘          └────────┬────────┘
                          (终态)                       │
                                                  advance
                                                       │
                                                       ▼
                                              ┌────────────────┐
                                              │    已完成        │
                                              │   yesno=2       │
                                              │   types=4       │
                                              └────────┬────────┘
                                                       │
                                                   (终态，可评价)
```

### 5.2 状态推进规则

| 当前状态 | 目标状态 | 触发接口 | 权限 |
|---|---|---|---|
| `types=1` 待审核 | `types=2` 已通过 | `POST /shenhe` (yesnoResult=2) | 仅管理员 |
| `types=1` 待审核 | `yesno=3` 已拒绝 | `POST /shenhe` (yesnoResult=3) | 仅管理员 |
| `types=2` 已通过 | `types=3` 进行中 | `GET /advance/{id}` | 管理员 或 订单所属用户 |
| `types=3` 进行中 | `types=4` 已完成 | `GET /advance/{id}` | 管理员 或 订单所属用户 |
| `types=4` 已完成 | — (终态) | — | 不可再推进，返回错误 |

> **advance 接口权限细节**：
> - 管理员（角色 != "用户"）可推进任意预约。
> - 普通用户只能推进 `yonghuId == session.userId` 的预约。
> - 前提条件：`yesnoTypes` 必须为 `2`（通过），被拒绝的预约无法推进。

## 7. 与宠物评价（ChongwuLiuyan）的衔接

### 7.1 评价前置校验

**核心规则：用户必须完成该宠物的预约（`yesnoTypes=2` 且 `types=4`）才能发表评价。**

```
ChongwuLiuyanController.save() / add()
  └─ chongwuYuyueService.hasCompletedBooking(userId, chongwuId)
       └─ SELECT * FROM chongwu_yuyue
          WHERE yonghu_id = ? AND chongwu_id = ?
            AND chongwu_yuyue_yesno_types = 2
            AND chongwu_yuyue_types = 4
          LIMIT 1
       └─ 结果为空 → 返回 511 "您尚未完成该宠物的预约，无法评价"
```

### 7.2 衔接流程图

```
  预约创建 ──▶ 审核通过 ──▶ 进行中 ──▶ 已完成 ──▶ 用户可发表评价
     │              │            │          │          │
     │         审核拒绝          │          │          │
     │              │            │          │          │
     │              ▼            │          │          │
     │           终态(不可推进)   │          │          │
     │                          │          │          │
     └──────────────────────────┴──────────┴──────────┘
                    ↑ 这些阶段均不可评价
```

### 7.3 校验覆盖范围

| 入口 | 是否校验 | 校验代码位置 |
|---|---|---|
| `POST /chongwuLiuyan/save`（后端） | **是** | 仅用户角色触发 |
| `POST /chongwuLiuyan/add`（前端） | **是** | 仅用户角色触发 |
| `POST /chongwuLiuyan/update` | **否** | 仅校验 IDOR 归属 |
| `POST /chongwuLiuyan/delete` | **否** | 无权限校验 |

> **注意**：管理员角色在 `save()` 中不受评价前置校验（代码 `if("用户".equals(role))` 分支内），管理员可以给任意宠物写留言。

### 7.4 评价与预约的关系说明

- 评价表 `chongwu_liuyan` 与预约表 `chongwu_yuyue` 之间 **没有外键关联**，仅通过 `(yonghuId, chongwuId)` 组合做存在性校验。
- 用户对同一宠物只要存在 **至少一条** 已完成预约，就可以发表评价，**不限制评价次数**。
- 评价可以在预约完成后的 **任意时间** 发表，无时效限制。

## 8. 时段冲突检测：当前实现与局限

### 8.1 当前实现

```java
// ChongwuYuyueServiceImpl.checkTimeConflict()
Wrapper eq("chongwu_id", chongwuId)
        eq("chongwu_yuyue_time", yuyueTime)       // ← 精确等值匹配
        in("chongwu_yuyue_types", {2, 3})          // 仅检查已通过和进行中
```

**调用点**：
| 调用位置 | 时机 | excludeId |
|---|---|---|
| `Controller.save()` | 创建预约前 | `null` |
| `Controller.add()` | 前端创建前 | `null` |
| `ServiceImpl.shenhe()` | 审核通过前 | 当前预约 ID（排除自身） |

### 8.2 局限性分析

| 局限 | 说明 | 风险等级 |
|---|---|---|
| **精确秒级匹配** | 仅拦截 `chongwu_yuyue_time` 完全相同的记录。预约 `10:00:00` 和 `10:30:00` 不视为冲突。 | **高** |
| **无时间范围/时长概念** | 预约表没有 `endTime` 或 `duration` 字段，无法判断时间段重叠。 | **高** |
| **仅按宠物维度检测** | 同一用户在不同宠物同一时段的预约不做拦截（合理，因为是上门服务到不同宠物）。 | 低 |
| **不检查拒绝/已完成** | `types ∈ {2, 3}` 以外的预约不参与冲突计算，已完成和已拒绝的不占名额。 | 合理 |
| **并发安全** | 未使用数据库锁或唯一索引，高并发下可能产生重复预约（当前业务量下风险极低）。 | 低 |

### 8.3 改进建议（仅供规划参考）

1. 增加 `chongwu_yuyue_end_time` 字段，冲突检测改为范围重叠判断：
   ```sql
   WHERE new_start < existing_end AND new_end > existing_start
   ```
2. 或在业务层引入时段枚举（如上午/下午/晚上），以字典管理。
3. 已创建数据库索引 `idx_chongwu_time_types (chongwu_id, chongwu_yuyue_time, chongwu_yuyue_types)` 可支撑后续优化。

## 9. IDOR 风险防护现状

> IDOR（Insecure Direct Object Reference）：不安全的直接对象引用，攻击者通过篡改 ID 访问他人数据。

### 9.1 已实现的防护

| 接口 | 防护措施 | 代码位置 |
|---|---|---|
| `GET /info/{id}` | 用户角色校验 `yonghuId == session.userId`，否则返回 511 | Controller 第 106-112 行 |
| `GET /detail/{id}` | 同上 | Controller 第 352-358 行 |
| `POST /update` | 用户角色校验归属 + 强制 `setYonghuId(sessionUserId)` 防篡改 | Controller 第 191-197 行 |
| `POST /save` | 强制 `setYonghuId(session.userId)`，不信任前端传入的用户 ID | Controller 第 149-150 行 |
| `POST /add` | 同上 | Controller 第 394-397 行 |
| `GET /advance/{id}` | 非管理员校验 `yonghuId == session.userId` | ServiceImpl 第 122-124 行 |

### 9.2 存在的风险点

| 接口 | 风险描述 | 风险等级 |
|---|---|---|
| `POST /chongwuYuyue/delete` | **无 IDOR 防护**：未校验角色或归属，任意登录用户可删除他人预约 | **高** |
| `POST /shenhe` | **无角色校验**：接口未检查调用者是否为管理员，理论上普通用户可构造请求自行审核（依赖前端菜单隐藏） | **高** |
| `GET /advance/{id}` | 管理员分支未做更细粒度权限控制 | 低 |
| `GET /chongwuYuyue/list` | `@IgnoreAuth` 注解，任何人可调用，依赖前端传参过滤 | **中** |
